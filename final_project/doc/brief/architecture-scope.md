## 怎麼用這份文件

老師的架構圖把專題分成 ①–⑩ 十個方塊。這份文件把每一塊整理成三段：

1. **老師要求**：講義對這一塊的說明（摘要，不是原文）。
2. **範圍選項**：分成「最低」「標準」「延伸」三檔。
   - 最低：能交差，但這一塊會被看成弱項。
   - 標準：能清楚展現這一塊的能力，是這次的預設目標。
   - 延伸：有餘力才做，Proposal 裡要標成 stretch 或 future work，不能寫成已承諾。
3. **決定**：勾選要做到哪一檔，並寫下理由。

建議是依照目前的條件給的：

- 實際上一個人做（名義上三人一組），只有週末時間。
- 每週大約用 30% 的 AI 訂閱額度。
- 手邊有 Arduino 和 Raspberry Pi 5，但不一定要用；不在車上加裝任何東西。
- 不預設有車友提供資料。
- Proposal 截止 2026-11-11。期末成果的截止日目前未知。

⑧⑨⑩ 不是要實作的模組，而是三個決策：選什麼領域、整體做到哪個 Level、用什麼證據證明成功。所以這三項的寫法和 ①–⑦ 不同。

## ① 使用者與應用情境（Users & Application Scenarios）

**老師要求：** 從「要替誰解決什麼問題」開始，不是從「要用哪個 AI 模型」開始。要回答三件事：Agent 是誰、服務誰、解決什麼真實問題。

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 一個使用者角色、一個情境，沒有證據說明痛點 |
| 標準 | 一個主要使用者角色；2–3 個具體情境，每個附一句使用者會問的話；痛點有公開資料或報告佐證 |
| 延伸 | 多個使用者角色，各自得到不同形式的輸出 |

**D1 的內容：**

- **Agent 是誰：** 一位懂台灣山路、天氣和你騎乘習慣的重機旅遊規劃專家。
- **服務誰：** 在台灣騎重機長途旅遊的騎士；第一位使用者是你自己，方法上任何人匯入自己的 GPX 都能用。
- **情境：**

| 情境 | 使用者會問 |
| --- | --- |
| S1 行程規劃 | 「週六想騎南橫來回，幾點出發才能天黑前回到家？」 |
| S2 出發前風險檢查 | 「明天下午山上會不會下雨？台 20 線有沒有封路？」 |
| S3 油量檢查 | 「這條路線中途要在哪裡加油？會不會遇到加油站沒開？」 |
| S4 騎乘中提醒（L3 延伸） | （不用問）預計抵達時間落後或前方天氣變差時，用耳機語音提醒 |

- **痛點證據（已查證）：** 台灣 2025 年道路死亡 2,858 人，只比前一年少 3.1%；交通部指機車族群死亡比例偏高、自摔自撞事故惡化。南橫 2025 年多次因地震和颱風預防性封閉（引用前要看原文）。

**決定：** ☐ 最低　☑ 標準（2026-10-25）　☐ 延伸
**理由：** 一個主要使用者加 3 個情境，足夠支撐 Introduction；多使用者角色（例如車隊、車友團）不預設有資料，不列入。

## ② 問題輸入與互動介面（Query Input & Interaction）

**老師要求：** 想清楚人要怎麼跟這位 AI 專家互動，選項有 Chat、Voice、Mobile、Web App、AR/VR。使用者用自然語言提問，系統要自己理解需要哪些資料和分析，不能要求使用者自己選資料表或演算法。

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 在 Notebook 或 CLI 輸入文字 |
| 標準 | Web 上的對話介面，能用自然語言提問，也能上傳或指定資料 |
| 延伸 | 加上語音輸入、手機介面，或 LINE Bot |

**D1 的內容：** Web 對話介面；可以用地名描述行程（「新竹出發，走南橫，當天來回」），也可以在地圖上點選；能匯入 GPX 建立或更新個人配速。規劃發生在出發前，騎乘中不需要操作畫面。

**決定：** ☐ 最低　☑ 標準（2026-10-25）　☐ 延伸
**介面技術：** 建議 Streamlit（一個人做最快），待定
**理由：** 語音只在 L3 的騎乘中提醒用到（單向播報），不做語音輸入。

## ③ 領域資料分析代理人（Domain Data Agent，核心大腦）

**老師要求：** Agent 不能只是把問題丟給 LLM、再把回答顯示出來。它要能拆解問題、決定要取哪些資料、呼叫哪些工具、做哪些分析，最後產生建議。標準流程是：

Understand → Plan → Acquire → Analyze → Generate → Interact（③-1 到 ③-6）

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 寫死的固定流程，LLM 只負責最後的文字解釋 |
| 標準 | LLM 當 Planner：依問題從固定的工具集裡選工具，可以多步執行，並依中間結果決定下一步 |
| 延伸 | 加上自我檢查和重新規劃（reflection / re-plan）、多個 Agent 分工、跨對話記憶 |

**各階段的內容（D1）：**

| 階段 | 這次要做的內容 |
| --- | --- |
| ③-1 理解需求 | 取出起訖點、途經路線、日期、限制條件（幾點前回家、避開下雨、最長騎乘時數）；缺資訊就追問 |
| ③-2 規劃推理 | 決定工具順序：路線 → 切路段算特徵 → 預測每段時間 → 依抵達時間查各段天氣 → 日落時間 → 加油站 → 風險評估 |
| ③-3 取得資料 | 路網與地形、氣象署預報、TDX 省道即時路況、加油站資料、自己的歷史 GPX |
| ③-4 資料分析 | 個人配速模型（含預測區間）、風險規則評分、油量與加油站距離計算 |
| ③-5 生成建議 | 建議出發時間（附範圍）、折返點、加油點、風險說明和出處 |
| ③-6 互動呈現 | 對話回答，加上地圖和時間軸 |

**延伸檔位的三個部分（D1）：**

1. **多 Agent 分工：**

| Agent | 負責 | 用到的工具 |
| --- | --- | --- |
| 規劃 Agent（Orchestrator） | 理解需求、拆解任務、分派給其他 Agent、彙整成計畫 | — |
| 配速分析 Agent | 預測每段路的騎乘時間和範圍 | 路線切段、地形、個人配速模型 |
| 天氣 Agent | 依各段預計抵達時間查天氣、日落時間 | 氣象署預報與觀測 |
| 路況與補給 Agent | 道路狀況、加油站位置與營業時間、續航檢查 | TDX、加油站資料、BMW 車系規格 |
| 驗證 Agent（Verifier） | 檢查整份計畫是否可行，不通過就退回規劃 Agent | 驗證規則 |

2. **驗證後重新規劃：** 驗證 Agent 檢查時間是否在日落前、各段時間加總是否一致、加油距離是否超過續航、回答中的數字是否都來自工具輸出；不通過就退回重新規劃，有次數上限。這是 D1 研究缺口的核心（LLM 規劃研究顯示，模型需要外部驗證器才能產生可行的計畫）。

3. **跨對話記憶：** 記住騎士的偏好（例如最長騎乘時數、是否接受碎石路、常用出發地）和過去的計畫，下次規劃時直接套用；每次匯入新 GPX 就更新個人配速。

**提醒：** Proposal 要求的 Pseudocode（Algorithm 1）主要就是描述這一塊；多 Agent 的訊息流也要畫進架構圖。

**決定：** ☐ 最低　☐ 標準　☑ 延伸（2026-10-25）
**理由：** 多 Agent 協作是目前正在做的方向，經驗可以直接沿用；驗證迴圈是和既有產品、既有研究的主要差別。工作量比標準檔大，L3 若時間不夠先延後。

## ④ 代理人六大能力（Agent Capabilities）

**老師要求：** ③ 講的是 Agent 怎麼工作，④ 講的是一位合格的領域代理人應該具備哪些能力。老師說這六項很適合直接當作專題評分指標，所以六項都至少要有。

| 能力 | 意思 | 最低 | 標準 | 延伸 | D1 的內容 | 決定 |
| --- | --- | --- | --- | --- | --- | --- |
| TALK | 自然對話、理解需求 | 單輪問答 | 多輪對話，能追問缺少的條件 | 語音或多語言 | 多輪對話，追問日期、回程時間等 | 標準 |
| KNOW | 專業知識 | 把知識寫在 prompt 裡 | 用 RAG 查文件、論文、規範，回答附出處 | 知識圖譜 | RAG：氣象署警特報定義、公路局道路資訊、騎乘安全資料、BMW 車系規格（油箱、油耗）、相關論文 | 標準 |
| SENSE | 取得真實資料 | 讀一份 CSV | 資料集加一個外部 API 或公開資料 | 即時 IoT 串流 | 自己的 GPX + 氣象署 + TDX + 加油站；L3 手機定位經 MQTT | 標準（L3 延伸） |
| ANALYZE | 統計、ML、預測 | 敘述統計 | 預測或異常偵測，並和 baseline 比較 | 模擬或最佳化 | 配速預測和 baseline 比較，含預測區間 | 標準 |
| THINK | 自主決策、規劃、選工具 | 固定流程 | LLM 選工具、多步推理 | 自我檢查、重新規劃 | 多 Agent 分工、驗證後重新規劃、跨對話記憶（見 ③） | 延伸 |
| SHOW | 呈現成果 | 文字加圖表 | 領域專用的儀表板加報告 | 主動警示推播 | 地圖（路段依時間和風險上色）、時間軸、可下載的行程計畫 | 標準（L3 語音提醒延伸） |

## ⑤ 資料來源與工具層（Data Sources & Tools Layer）

**老師要求：** 這一層是 Agent 的眼睛、耳朵、記憶和工具箱。Agent 不必擁有所有資料，但要知道什麼時候該用哪一種來源。核心觀念是：LLM 不必自己做所有事，好的 Agent 知道什麼時候該用什麼工具。

| 子層 | 內容 | 要用嗎 | D1 的來源 |
| --- | --- | --- | --- |
| ⑤-1 IoT Data | 感測器、ESP32、Arduino、MQTT、即時串流 | 部分 | 車載 App 記錄的 GPX（約 1 秒一點）；L3 延伸：手機定位經 MQTT 即時回傳 |
| ⑤-2 Internal Data | 資料庫、CSV、Excel、歷史資料、SOP | ☑ | 279 趟歷史 GPX（原始檔不進 repo） |
| ⑤-3 External Data | Web Search、公開資料、天氣、第三方 API | ☑ | 氣象署預報、觀測、日出日落；CODiS 歷史天氣；TDX 省道即時路況；中油、台糖加油站；OpenStreetMap 路網；內政部地形（要用 DTM，不用 DSM）；公路局急彎、陡坡資料 |
| ⑤-4 Knowledge Base | PDF、論文、技術文件、法規，用向量資料庫或知識圖譜檢索 | ☑ | 氣象署警特報說明、公路局行車資訊、騎乘安全資料、BMW 車系規格、相關論文 |
| ⑤-5 Analytics Tools | Python（Pandas、NumPy）、ML、時間序列、視覺化 | ☑ | pandas、scikit-learn、statsmodels、LightGBM、OSMnx、地圖比對工具（Valhalla 或 FMM）、Google Maps Platform（地圖顯示、路線與預估時間） |

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 一份公開資料集加上 Python |
| 標準 | 公開資料集、一個外部來源，再加一個領域知識庫 |
| 延伸 | 加上即時 IoT 串流，例如 Raspberry Pi 透過 MQTT 送資料 |

**已知缺口：** 道路阻斷沒有找到機器可讀的 API 和歷史紀錄；先用 TDX 即時路況，阻斷資訊列為延伸。

**提醒：** 如果用 Raspberry Pi 重播資料集來模擬感測器，文件和簡報都要寫明是「重播（replay）」，不能說成真實感測器量到的資料。

**決定：** ☐ 最低　☑ 標準（2026-10-25）　☐ 延伸（L3 時加上即時串流）
**理由：** 自己的 GPX 加多個官方開放資料和知識庫，已超過標準檔的要求；即時串流依 ⑨ 放在 L3。

## ⑥ 分析引擎（Analytics Engine）

**老師要求：** 這是「資料分析」課和一般生成式 AI 課的分界。取得資料後，必須真的做資料處理、統計、機器學習、預測、異常偵測、模擬或最佳化。核心原則是：

> LLM 負責理解、推理和解釋；Analytics Engine 負責計算、驗證和提供證據。

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 敘述統計加一個迴歸模型 |
| 標準 | 2–3 種方法，和 baseline 比較並有評估指標。baseline 可以用課堂教過的 L5 自迴歸和 L6 多元線性迴歸 |
| 延伸 | 加上 what-if 模擬、最佳化、不確定性估計 |

**方法清單（D1）：**

| 分析任務 | 方法 | Baseline | 指標 |
| --- | --- | --- | --- |
| 路段騎乘時間預測（核心） | 多元迴歸（L6）→ 梯度提升樹（LightGBM，分位數損失給 P50 / P90） | 平均速度、速限換算、Google Maps 預估時間（機車模式若可用） | 路段與整趟的 MAE、MAPE；P90 區間覆蓋率；依行程分組交叉驗證，加上最新行程的時間外推 |
| 天氣與路況風險評分 | 透明規則，門檻取自氣象署警特報 | 無（沒有正確答案） | 用歷史封路日回測的命中率、敏感度分析、案例研究；不宣稱預測事故 |
| 油量檢查 | 續航計算 + 加油站距離與營業時間 | — | 案例檢查 |
| 天黑前回程判斷 | 預測區間 + 日落時間 | — | 用歷史行程回測 |

**提醒：** L4-2 教的 CRISP-DM 流程（Business Understanding → Data Understanding → Data Preparation → Modeling → Evaluation → Deployment）可以直接當這一塊和 Experiments 的寫作骨架。

**決定：** ☐ 最低　☑ 標準，含預測區間（2026-10-25）　☐ 延伸
**理由：** 預測區間（延伸中的不確定性估計）對「天黑前回得來嗎」這種問題是必要的，而且分位數損失幾乎不增加工作量；what-if 模擬和最佳化不列入。

## ⑦ 輸出與互動呈現（Output & Interface）

**老師要求：** 分析的目的是讓人看懂並採取行動，輸出不限於文字，可以是 Chat UI、Dashboard、圖表、地圖、報告、設計圖或警示。不同專業的 Agent 應該有不同的專業工作介面，不要每一組都長成同一個聊天視窗。

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 文字回答加上幾張圖表 |
| 標準 | 對話加一個領域專用的儀表板，再加一份可下載、附證據和出處的報告 |
| 延伸 | 主動警示推播（Email 或 LINE）、地圖、3D 呈現 |

**D1 的內容：**

- 對話回答。
- 行程儀表板，**地圖用 Google Maps**：路線依各段預測時間和風險上色；標出加油站、預計抵達各點的時間；時間軸標出日落時間；比較不同出發時間的結果。
- 可下載的行程計畫：路線、時間範圍、加油點、風險和出處。

**Google Maps 的注意事項（待確認）：**

- 要用 Google Maps Platform 的 API 金鑰，並綁定帳單帳戶；費用和免費額度要先查清楚。
- Google 的路線服務若支援機車模式，它的預估時間可以直接當 ⑥ 的 baseline（「一般導航的時間」vs「個人配速模型」）；台灣是否支援要實測。
- 依 Google 的使用條款，Google 提供的路線和時間要顯示在 Google 地圖上，不能搬到其他地圖。

**決定：** ☐ 最低　☑ 標準，含 Google Maps（2026-10-25）　☐ 延伸（L3 時加上騎乘中語音提醒）
**理由：** 地圖本身就是這個領域的專業介面；Google Maps 是騎士最熟悉的地圖，路線和預估時間也能當比較基準。推播依 ⑨ 放在 L3。

## ⑨ 實作難度與學習路徑（Implementation Levels）

**老師要求：** 分三個 Level，依能力逐步往上，不要求一開始就做 Autonomous Agent。

| Level | 內容 |
| --- | --- |
| L1：LLM + Data | 對話介面、讀 CSV 或 API、Python 分析、圖表呈現。先打通「問題 → 資料 → 分析 → 回答」 |
| L2：Knowledge Agent | 加上 RAG 文件檢索、Web Search、API、多步推理，具備真正的領域專業 |
| L3：IoT Autonomous Agent | 加上 IoT 感測器、MQTT、即時資料流、進階分析、主動警示，不必等人提問就會持續觀察 |

**這一項是決策：** 整體要做到哪個 Level。

**決定：** ☐ L1　☐ L2　☑ L2 + L3 延伸　☐ L3（2026-10-24 決定）
**理由：** 實際一人、週末進行，承諾 L2 可以穩定交付；L3（IoT 即時串流、主動警示）畫進架構圖但標成延伸，期末有餘力再做。
**D1 的 L3：** 騎乘中手機定位經 MQTT 回傳家裡的 RPi 5，即時更新預計抵達時間，落後或前方天氣變差時用耳機語音提醒；不在車上加裝東西。

## ⑩ 課程成果與評量（Outcomes & Evaluation）

**老師要求：** 成功的作品不看用了多少 AI 套件，也不只看畫面好不好看，而是看 Agent 有沒有真正的價值。期末展示要能講清楚：打造了什麼樣的 AI 專業代理人、服務誰、取得哪些資料、如何分析、根據什麼知識判斷、替使用者解決了什麼問題。

**這一項是決策：** 每項成果要用什麼證據來證明。

| 老師的成果項目 | D1 要提出的證據 |
| --- | --- |
| 解決真實問題 | 台灣 2025 道路死亡與機車事故數據、山區道路封閉紀錄、3 個具體情境 |
| 資料來源多元 | 自己的 GPX、氣象署、TDX、地形、路網、加油站、知識庫 |
| 資料分析具有深度 | 配速模型和多個 baseline 的比較、預測區間、依行程分組驗證 |
| 能引用專業知識 | 回答附出處（氣象署、公路局、騎乘安全資料、論文）；Deep Research 的思維模式與爭議 |
| 介面設計有創意 | 地圖依路段時間和風險上色、時間軸、出發時間比較 |
| 對使用者有價值 | 用過去的行程回測：「如果當時用這個工具規劃，預測的回程時間和實際差多少」 |

**範圍選項：**

| 檔位 | 內容 |
| --- | --- |
| 最低 | 在資料集上算出離線評估指標 |
| 標準 | 加上和 baseline 的比較，以及 2–3 個完整的案例示範 |
| 延伸 | 加上消融實驗（例如有無知識庫的差異），或找幾位同學做小型使用者測試 |

**加做的消融實驗：** 準備約 20–30 題規劃問題，比較「只用 LLM」「LLM + 知識庫」「完整 Agent（工具 + 驗證迴圈）」三種做法的計畫可行率和時間誤差。這直接對應 D1 的研究缺口。使用者測試不列入。

**提醒：** Proposal 階段還沒做實驗，Abstract 的 F 段只能寫預期成果，不能編造結果。

**決定：** ☐ 最低　☑ 標準，加一項消融實驗（2026-10-25）　☐ 延伸
**理由：** 消融實驗工作量小，又能證明 Agent 比單純聊天機器人可信，是 Proposal 最有力的賣點。
