01全景：人類核准一次，Agents 在邊界內完成governance§1.1 · §1.2 · §1.4 · §1.5 · §3.4 · §3.5

人類 acceptor 一次接受並授權 Outcome Contract；之後依 lane 自主執行到自然完成。需要判斷時派工給有權角色，不是停下來等人。只有下方四種 boundary 才回到人類，而且只停止受影響的路徑。

完整規則：Outcome Contract、re-authorization 與 §1.5§1.2 · §1.4 · §1.5 · §3.8
  • 三種權限分開：接受工作要求、授權執行、確認設計語義。同一有效指令可一併完成接受與授權，但 Agent 不得推定超出該指令的效果。接受與授權屬 Bindings 宣告的人類 acceptor（或其已記錄的 standing authorization）；設計語義屬 Design Authority；其他角色只能 route（§1.2）。
  • Derived contracts：每份 MUST 可追溯至 Outcome Contract 條款，並附 DA 的 derivation record（依據、boundary determination、該 Spec 分配到的 acceptance boundary 部分、受影響工作）。
  • Re-authorization 只在三種情況：結果超出 scope／constraints；改變 accepted 語義；Bindings §5.2 的 reserved boundary。Boundary 疑義先 route DA；DA 無法確立在 boundary 內時受影響路徑 fail-closed 至 acceptor。Reviewer 的 boundary finding 在 DA determination 後仍有爭議，同樣 fail-closed；FA MAY 裁決 routing／process 爭議，MUST NOT 代 acceptor 裁決 boundary 本身。
  • Agents MUST NOT 自行發起 Outcome Contract。Follow-up、deferred disposition 與 non-blocking finding 的後續事項在被接受並授權前只是 tracked items。契約內必要的 rework／re-verification 不是新工作接受 gate。
  • §1.4 下列事項本身不是等待 operator 的理由：work item／phase 完成；需要新 session 或 agent replacement；findings、rework、audit escalation；DA decision、FA 或 phase adjudication；context rollover；promotion 所需的授權內設計工作。
  • Recovery 何時成為 boundary（§1.5）：完成 (1) 從權威紀錄 re-ground、(2) 依 replacement policy 替代或修復、(3) DA／FA routing 已裁決或確認無法裁決，三項之後仍 unsafe／indeterminate，才停止該路徑；停止紀錄寫明現況、缺少事項、已嘗試的動作與結果、所需 authority 與下一步。結果無法確認且可能已有不可逆副作用的 assignment，使該路徑 unsafe。
  • 完成（§3.8）：符合契約、self-verification 與 gates、必要 audit／adjudication、無未處置 blocking、無未決 design ambiguity、最終產物有 coverage、worklog 已更新。Run completion、work item completion、phase acceptance 與 release authorization MUST 分別陳述。

完整規則：Work Contract 七項 properties、Formal 必備條件、promotion§3.1 · §3.3 · §3.4 · §3.6 · orch §3

Work Contract 的七項 properties（§3.1）：Intent and outcome · Scope and boundaries · Acceptance and verification（每條需要 verification 的 AC 有可觀察的 PASS／FAIL 語義與充分證據要求；Outcome Contract 的 acceptance boundary 足以判定 derived Specs 的分配涵蓋）· Authority and authorization（Outcome Contract 的授權明示涵蓋規劃至完成，或明示 §5.2 保留的動作）· Relevant context · Assurance path · Stable reference。可由短 prompt、既有 accepted decisions 與專案預設共同滿足。

Formal 必備（§3.4）：有效且涵蓋 scope 的 Outcome Contract 接受與授權（Bindings 保留 implementation authorization 時另有紀錄）；DA derive、implementation-ready 的 Spec／Tickets 附 derivation record；明確 dependencies、AC、invariants 與證據要求；Orchestrator run-to-completion；整合驗證、Spec Integration Audit 與 DA phase acceptance。Parent Spec 仍把必要設計留待下游時，不是 implementation-ready。Tickets 不得重新定義 AC 的 PASS／FAIL 語義。

Orchestrator activation 的五項前提（orch §3）：(1) 已接受並授權的 Outcome Contract 與 authority record；(2) DA derive 的 Spec／Tickets 與 derivation record（含 boundary determination）；(3) §5.1 bindings 就緒、definitions 與有效 mapping 存在、PROJECT_BINDING 已填、無 TBD；(4) §2.3 independent dispatch 機制已宣告；(5) work records 權威位置已配置。Designation 是 acceptor／operator 的行為，有可持久引用的紀錄，不構成 Outcome Contract 的接受或授權。對自身 model／effort 的核對 MUST 先於第一次 dispatch。缺任一前提時不啟動 run。

§3.6 必須直接 route DA、不必耗盡 R1／R2 的情況：contract 有兩種以上會影響實作的合理解讀；實作必須猜測 measurement／lifecycle／identity／ownership 語義；修正 finding 需要改變 invariant；Reviewer disagreement 實質上是 architecture／requirement decision。

B 類的判準：工作引入的產品／系統行為、介面、invariant 或 gate 沒有 accepted baseline 而其他工作將依賴它；所需裁決會改變 accepted 語義（同時是 §5.3 contract change，須先經 acceptor）；parent 將必要選擇留待下游。行政作業慣例（通知、進度同步、摘要、文件維護）不改產品行為與 assurance 時不屬此項，屬 Bindings 內容的變更。需要 Spec 的判準是語義需要設計，不是篇幅或檔案數量。

Promotion MUST：保存原 contract、worklog、產物、verification 與 findings；記錄理由及有權決定；把已完成與未完成內容對應到 Spec／Tickets；由相應 authority 確認既有 evidence 的可用範圍；保留未解 findings，不藉換 lane、換 ID 或建新 Ticket 清空 audit history。

Completion predicates（orch §7）：P1 dependencies · P2 授權與引用鏈 · P3 self-verification evidence 與 required gates · P4 必要 audit 已 closure · P5 無未處置 blocking · P6 已 route 的 design questions 有 decision record · P7 最終 subject 有 coverage · P8 worklog 已更新 · P9 整合驗證 · P10（Spec-level）Spec Integration Audit closure 且被 phase acceptance 引用。失敗的 required gate 不因 FA ruling 或 disposition 視為滿足。

  • 更新時機：在足以支援 handoff／recovery 的時間點更新，不得只靠結案後回憶補寫；中斷後補建的內容區別可驗證事實與未知事項。
  • Worklog 不能：取代 Work Contract、Spec、Ticket、audit record 或原始 evidence；創造 authority 或使未核准假設成為 requirement；把 Executor 的「已修正」變成 Reviewer closure。MAY 以引用連結證據；MUST 可由接手 session、Orchestrator 或 Reviewer 取得並理解。治理不指定檔名、schema 或 storage。
  • 不是 stop 條件（§1.4、orch §9、Appendix A）：work item 完成、phase boundary、需要新 session／replacement、findings／rework／escalation、DA 或 FA 裁決、rollover、promotion 所需設計工作。Rollover 是 internal act：checkpoint → successor 以同一 run identity 與 designation 從權威紀錄 bootstrap，重新 grounding 並核對自身 model／effort。

  • §5.4 不規定：Ticket lifecycle state machine、特定 validator、schema、Git branch／trailer、transcript parser、rollover／heartbeat 演算法、恢復重試次數、具體 model、能力層分類、價格、effort 名稱、alias、trigger 的具體條件與替代順序、bounded assignment 的具體類型（V22-21）。不得只以文字宣稱尚未具備的 isolation、binding 或 recovery 能力。
