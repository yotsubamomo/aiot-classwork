01核心 operating modelgovernance§1.1 · §1.2 · §1.4 · §1.5

人類的固定職責是一次接受並授權 Outcome Contract，以及 §1.5 四項 boundary 內的決定；其餘保留給人的動作由 Project Bindings 明確枚舉（§5.2，採 opt-in）。契約成立之後，判斷不是停止條件，而是 routing 條件——需要別的 authority 時派工給該 authority，取得可追溯裁決後繼續，直到自然完成。

五項共同 invariants（§1.1 為索引；完整規範以所引條文為唯一 authoritative definition）§1.1

1 · Autonomous orchestration

→ §1.4、§1.5、§3.8。Orchestrator 啟動後，work item 完成、phase boundary、replacement、findings、裁決、rollover 本身 MUST NOT 成為等待 operator 的理由；只有 §1.5 四項 boundary 才可停止受影響路徑；run 在授權工作完成或剩餘工作皆受真正 boundary 阻擋時才可結束。

2 · Explicit roles and verifiable bindings

→ §2.1–§2.3。每個實際使用的 Agent／Subagent MUST 有明確 definition（responsibility、authority、prohibited authority、independence requirement）；每個可 dispatch identifier MUST 有明確 mapping；每個實際 assignment MUST 可驗證。核對的內容依 §2.2 分兩種（第 04 節）。

3 · Independent audit integrity

→ §2.3、§4.1–§4.7。所有正式 audit MUST 遵守 §2.3 四項 properties；一旦被要求或選擇，均適用同一套 R1／R2／一次 Alternate／Final Adjudication 流程，不另設 lightweight review；Spec Integration Audit 適用同一套規則。

4 · Agent-autonomous decisions

→ §1.3、§2.4。角色權責以 §2.1 表為唯一權威定義；substantive decision owner 與 routing 依 §2.4；Orchestrator MUST 依表派工，MUST NOT 判斷設計語義、finding severity 或 evidence sufficiency。

5 · Mandatory durable worklog

→ §3.7。每個已執行 work item MUST 有足以支援 traceability、handoff 與 recovery 的 durable worklog；§3.7 是唯一規範定義（第 06 節）。

三種不同權限

接受工作要求、授權執行、確認設計語義是三種權限。前兩者屬人類 acceptor（或其已記錄的 standing authorization），後者屬 Design Authority。任一角色遇到另一種權限的問題只能 route，不能代行（§1.2）。在已接受的 Outcome Contract 內產生 derived contract 是設計行為，不是接受或授權行為（§5.2）。

Need for judgement is not a stop condition. It is a routing condition.

02Outcome Contract、derived contracts 與雙 lanecontract§1.2 · §3.1 – §3.6 · §5.3

第一級 abstraction 仍是 Accepted Work Contract；契約的成立依據是 §3.1 的七項 properties，不是文件形式。v2.0 把由人類 acceptor 接受並授權的 Work Contract 命名為 Outcome Contract：Lightweight 下就是被接受的 prompt、brief 或 Jira item；Formal 下 Spec 與 Tickets 是 Design Authority 在 Outcome Contract 內產生的 derived contracts，其接受與授權來自 Outcome Contract，不來自 Design Authority，也不需 acceptor 逐份核准。

Work Contract 的七項 properties§3.1

  1. Intent and outcome — 要解決什麼問題，預期產出或行為為何。
  2. Scope and boundaries — 可變更範圍、重要 non-scope 與適用限制。
  3. Acceptance and verification — 對每條需要 verification 的 AC，定義或引用可觀察的 PASS／FAIL 語義與充分證據要求。對 Outcome Contract，acceptance boundary MUST 可觀察到足以判定每份 derived Spec 的 AC 是否涵蓋其 derivation record 所分配的部分，以及全部 derived Specs 合起來是否涵蓋它；Spec 的具體 AC 由 Design Authority 在該 boundary 內 derive。Tickets、Executors 與下游 Skills MUST NOT 自行重新定義。
  4. Authority and authorization — 誰接受此要求、允許哪些執行與決定。對 Outcome Contract，授權 MUST 明示涵蓋規劃、分解、實作、審查、修正至完成，或明示依 §5.2 保留的動作。
  5. Relevant context — 必要依賴、適用既有契約與已知風險。
  6. Assurance path — 採用何種 lane，以及依 §4.1 確定的 audit 與其他 gate 要求。
  7. Stable reference — 可識別、可持久追溯的 accepted 內容或版本。
這七項可以由短 prompt、既有 accepted decisions 與專案預設共同滿足，不要求每項各設欄位，也不要求新增文件。未明示的例行 implementation detail 由 Executor 決定；但契約 properties 的缺口不得以 implementation choice 名義補齊。

accepted 語義 vs accepted contract§1.2

  • accepted 語義專指 acceptor 接受的 Outcome Contract 之 intent、scope、constraints 與 acceptance semantics；derived contract 的內容是 Design Authority 的設計，其變更依 §5.3 區分。
  • accepted Work Contract／accepted contract 涵蓋 Outcome Contract 及其有效 derived contracts；finding、gate 與 completion 所對照的契約條款包含 derived contract 的 AC、invariant 與 gate。
  • 每份 derived contract MUST 可追溯至其 Outcome Contract 條款，並附 Design Authority 的 derivation record（依據、boundary determination、該 Spec 所分配的 Outcome Contract acceptance boundary 部分、受影響工作）。

Agents MUST NOT 自行發起 Outcome Contract；derived contracts 依 §1.2 在已接受的 Outcome Contract 內產生，不屬自行發起。Follow-up、deferred disposition 與 non-blocking finding 的後續事項，在 acceptor 接受並授權前只是 tracked items。

Lightweight eligibility 的 routing conditions§3.3

成立條件是 Executor 能在不對 properties 1–4 作出任何假設的前提下完成工作。第一個必須作出的此類假設即為 routing condition：

  • 語義缺口（scope 邊界、acceptance 判準、intent 解讀）→ MUST route 至 Design Authority，依 §3.6 處理。
  • 接受／授權缺口（是否真的要做、property 4 未明）→ MUST route 至 acceptor；在 Orchestrator run 內是 §1.5 boundary，只停止受影響路徑。
  • boundary 缺口（是否允許動到某範圍、所提變更是否仍在 Outcome Contract 內）→ 依 §1.2 先 route 至 Design Authority 作 boundary determination；DA 無法確立時 fail-closed 至 acceptor。

Lane eligibility 依預期的整體結果判定，不依本次增量判定。累積 scope 與 remaining work MUST 可由 worklog 追溯。

Contract change 只有兩類（§5.3，唯一規範定義；§3.3、§3.4、§3.6 引用之）：① 改變 accepted 語義（Outcome Contract 的 intent、scope、constraints 與 acceptance semantics），或改變其他工作所依賴的設計基線 → contract change：route Design Authority 判定性質與影響，走該 Outcome Contract 原本的 acceptor，必要接受與授權成立前不執行依賴變更後語義的 implementation；② 不改變 accepted 語義的 derived contract 設計、修訂與 clarification → 由 Design Authority 以 derivation／decision record 決定並處理對進行中工作、dependencies 與既有 evidence 的影響，不觸發 acceptor 核准。不設第三類「additive」：新增了 Outcome Contract 未涵蓋的 requirement、AC 或 scope 即屬第 1 類。
行政作業慣例 ≠ 設計基線（IR-1 已併入 §3.3、§3.6-B）：通知、進度同步、結果摘要、文件維護等行政作業慣例，若不改變產品行為、驗收標準、完成條件、角色權限、安全控制與必要 assurance，不屬 §3.6-B 第 1 項的設計基線；其新增或調整是 §5.1 Bindings 內容的變更，依 §5.3 留下版本、依據與授權，不依承載檔名觸發任何 lane 或 audit。
Promotion 的 continuity（§3.6）：保存原 contract、worklog、產物、verification 與 findings；記錄理由及有權決定；將已完成與未完成內容對應至 Formal Spec／Tickets；由相應 authority 確認既有 evidence 的可用範圍；保留未解 findings，不藉換 lane、換 ID 或建新 Ticket 清空 audit history。Promote 後的 Spec 是原 Outcome Contract 內的 derived contract；超出原 boundary 者依 §1.2 re-authorization。

只有一套正式 audit semantics。差別只在「是否觸發」，不在品質：Formal 每個 work item 必須執行，每份 Spec 另 MUST 執行 Spec Integration Audit；Lightweight 依 accepted contract、Project assurance policy、使用者要求或有權裁決決定。不另設 lightweight review，不增加 R3／R4。

Audit applicability§4.1

  • Formal／SDD：每個 work item 的 independent audit MUST 執行；每份 Spec 另 MUST 執行 §4.7 的 Spec Integration Audit。
  • Lightweight：依 accepted contract、Project assurance policy、使用者要求或有權裁決決定。
  • 使用者明確要求 audit 時 MUST 執行；已宣告的必要 audit 不得由 Executor 或 Orchestrator 取消。
  • 未配置或無法確認適用性時 MUST route 至 Design Authority，不得靜默選擇不審查。

工作大小或缺少 Spec 不是免除 audit 的充分理由。Audit applicability 與 SDD eligibility 是不同問題。

Findings 與 blocking§4.2 · §4.3

  • 每項 finding MUST 有可追溯識別、證據、severity 與 blocking 判定。
  • Blocking MUST 依 accepted contract 或宣告 operating scope 內的具體實質風險，不得以個人偏好創造需求。
  • 預設 Critical／High 為 blocking；Medium 由 Reviewer 明確分類；Low 為 non-blocking。Non-blocking findings MUST 記錄 disposition；需後續處理者須有 owner，但不得延長當前 audit cycle。
  • Blocking status 或 review evidence 有爭議 → Final Adjudicator；爭議實質涉及設計語義 → 先交 Design Authority。

契約語義不足時，Reviewer 提出具體 ambiguity 並 route 至 Design Authority。契約不足是 routing signal，不是對 implementation 的 blocking finding，也不觸發 promotion（§4.2）。

Disposition 邊界§4.5

Blocking finding 可被 deferred，僅限以下條件同時成立：

  1. 該 finding 不主張違反 accepted contract 條款。主張契約違反者只能 dismiss（附推翻該主張的證據）、要求 rework，或作為 contract change 交 Design Authority 與 acceptor。
  2. 殘餘風險在宣告的 operating scope 與 assurance policy 之內，或風險條件在宣告 envelope 之外。
  3. 有 owner 與 tracked item；tracked item 在被接受前不是新工作（§1.2）。
  4. Disposition 記錄理由，且不將任何 gate 標為 PASS。

Assurance policy 宣告為高風險類別的 blocking finding，deferral MUST 另有 Design Authority 的確認並記入 disposition；Final Adjudicator 不得單獨 defer。Final Adjudicator MUST NOT 虛報 gate PASS、以 disposition 隱性修改 requirement、覆寫原 Reviewer 結論、取得其他 authority 的保留權限，或只因需要判斷就要求 operator 介入。

Cycle 起點與進展（§4.5）。新的 bounded cycle 一律從 R1 開始，且只有兩個合法起點：Final Adjudicator 授權的 material rework（授權 MUST 指明相對於前一 cycle 受審 subject 有何實質改變）；或 Design Authority 的 contract change 使受審 subject 或其契約失效。Subject 與契約皆未改變時，不得開新 cycle；改 lane、換 model 或重命名 work item 不構成 reset 理由。同一 root cause 的 blocking finding 在新 cycle 的 R2 之後仍未解時，不再視為 rework 可解的 implementation defect，MUST 交 Design Authority 或在 disposition 邊界內處置。本治理不設 cycle 總數上限；上述進展條件即為 bound。

06Mandatory durable worklogexecution§3.7

Work item ＝ 一個 accepted Work Contract 的一次執行。
Formal 下以 Ticket 及其引用的 Spec 構成契約；Lightweight 下以被接受的 brief、prompt 或 Jira item 等構成契約。

是同一個 work item

  • 同一契約執行的續接 session更新同一 worklog identity，不因 session replacement／rollover 另開工作身分
  • 由 Orchestrator 派工、由 direct execution session 執行、或由任何其他 session 接手，義務相同
  • 中斷、失敗、取消或無產物變更的執行，同樣要留下 worklog

不是新的 work item

  • Sub-agent action
  • Command
  • File edit

不產生 worklog 義務

  • 純詢問
  • 尚未成為 accepted execution 的探索
  • 未被接受的請求

最低內容（兩條 lane 相同）§3.7

  1. Work performed — 實際做了什麼，以及目前結果。
  2. Contract reference — Accepted Work Contract、適用版本及重要變更。
  3. Executing role and binding reference — 執行角色與實際 binding 證據引用；不要求複製 Harness 日誌。
  4. Decisions and assumptions — 重要實作決定、假設，以及需要 authority 的決定所引用的 ruling。
  5. Artifacts — 主要新增、修改或移除的產物及可識別版本。
  6. Verification — verification／test 方法、結果、限制及 evidence 引用。
  7. Audit status — required／elected／not required、其依據與實際進度；有 audit 時引用 records、findings 與 dispositions。
  8. Remaining work — 累積 scope、未完成事項、阻擋原因、負責者／authority 與下一步。

更新時機與誠實性

  • MUST 在足以支援 handoff／recovery 的時間點更新，不得只依賴成功結案後回憶補寫。
  • 中斷後補建的內容 MUST 區別可驗證事實與未知事項。
  • MUST 可由接手 session、Orchestrator 或 Reviewer 取得並理解。
  • MAY 以引用連結證據，無須複製完整 logs。

Worklog 不能做的事

  • 不取代 Work Contract、Spec、Ticket、audit record 或原始 evidence
  • 不創造 authority，不使未核准假設成為 accepted requirement
  • 不把 Executor 的「已修正」變成 Reviewer closure

§3.7 是 worklog 要求的唯一規範定義。治理不指定檔名、schema、storage、更新工具，也不要求一個 worklog identity 必須對應一個實體檔案。
